1 — What a Request Body Is, and Your First Pydantic Model

How does an API receive a whole new record in one request, instead of one value at a time? A request body is the JSON data a client sends along with its request. You send one whenever the data has many parts: a new sign-up, order or enquiry. A simple value like an id still belongs in the path or the query string.

FastAPI needs to know the shape of that JSON before it can trust it. A Pydantic model is a Python class that names each field and its type. You build one by subclassing BaseModel; Pydantic then checks and converts the data the moment you create it.

Where a value comes fromOne small value    → a path or query parameter
A whole new record → a request body, described by a model

class Item(BaseModel) — one model, two typed fields

Pydantic checks each value against its type, and converts it when it safely can.

You type 
from pydantic import BaseModel


class Item(BaseModel):
    name: str
    price: float


item = Item(name="Pen", price="15.0")
print(item)
print(item.model_dump())
Python shows 
name='Pen' price=15.0
{'name': 'Pen', 'price': 15.0}
  1. class Item(BaseModel): starts a model by subclassing BaseModel.
  2. name: str and price: float are typed fields, one per line.
  3. item = Item(name="Pen", price="15.0") turns the text "15.0" into a real float.
  4. print(item.model_dump()) shows the model's data as a plain dictionary.

Reach for a model whenever a piece of data has more than one or two related fields.

2 — Receiving the Body, Required and Optional Fields

How does your endpoint actually get that whole JSON object?

You add a parameter typed as your model, and FastAPI reads the request body into it before your function runs. Not every field has to arrive. A required field has no default, so a request missing it is rejected. An optional field gets a default value, which fills in when the field is left out.

🌟 Case Study: Opening the Enquiry Form to Real Requests

Future Vision's website form also asks for the branch. A visitor can skip how many follow-ups they expect, or add a note.

follow_ups: int = 0 — a default fills the gap

Building the model with only the required fields still works; the optional ones fall back to their defaults.

You type 
class EnquiryIn(BaseModel):
    name: str
    phone: str
    course: str
    branch: str
    follow_ups: int = 0
    notes: str | None = None


enquiry = EnquiryIn(name="Priya Mehta", phone="9825012345", course="Python Professional", branch="Citylight")
print(enquiry.follow_ups)
print(enquiry.notes)
Python shows 
0
None
  1. follow_ups: int = 0 is optional; it falls back to 0 when left out.
  2. notes: str | None = None is optional too, and falls back to None.
  3. name: str stays required, with no default after the type — phone, course and branch work the same way.

This program runs for real, so FastAPI itself checks a request, not just a direct call in Python.

You type 
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class EnquiryIn(BaseModel):
    name: str
    phone: str
    course: str
    branch: str
    follow_ups: int = 0
    notes: str | None = None


@app.post("/enquiries", status_code=201)
def create_enquiry(enquiry: EnquiryIn):
    return enquiry.model_dump()


if __name__ == "__main__":
    import uvicorn

    uvicorn.run(app, host="127.0.0.1", port=8000)

3 — Add Simple Validation Rules with Field()

A type hint alone only checks the kind of value you got, not whether it makes sense. Field() adds a validation rule on top of the type, a check your data must pass before the model is built. You write it as the field's default.

Common rules include min_length and max_length for text, and ge (at least) and le (at most) for numbers. A failed rule raises ValidationError, with a plain message naming what went wrong.

🌟 Case Study: Catching a Too-Short Name or an Impossible Age

A one-letter name or an age of 120 are real mistakes a counsellor would want FastAPI to catch early.

Field(min_length=2) — reject a name that is too short

A valid name builds normally; a name under the minimum length raises an error instead.

You type 
from pydantic import Field, ValidationError


class EnquiryIn(BaseModel):
    name: str = Field(min_length=2)
    age: int = Field(ge=5, le=80)


print(EnquiryIn(name="Priya Mehta", age=19))

try:
    EnquiryIn(name="P", age=19)
except ValidationError as e:
    print(e.errors()[0]["msg"])
Python shows 
name='Priya Mehta' age=19
String should have at least 2 characters
  1. name: str = Field(min_length=2) replaces the plain type with a rule.
  2. age: int = Field(ge=5, le=80) keeps age inside a sensible range.
  3. except ValidationError as e: catches the failure instead of crashing the script.

Field(ge=5, le=80) — reject an age outside the range

The same model also rejects an age of 120, well past le=80.

You type 
try:
    EnquiryIn(name="Priya Mehta", age=120)
except ValidationError as e:
    print(e.errors()[0]["msg"])
Python shows 
Input should be less than or equal to 80
  1. EnquiryIn(name="Priya Mehta", age=120) fails only the le=80 rule; the name is fine.

Add these same Field() rules to the enquiry form's model from section 2. Then a request with age=120 gets a 422, the same way a missing phone did.

4 — Use a List and a Nested Model

Some fields hold more than one value of the same kind. A list field is written list[...], with the item type inside the brackets, like list[str]. Pydantic checks every item inside it, not just the list as a whole.

Other data is naturally grouped. A nested model is one model used as the type of another model's field. A group of related values travels together that way. Pydantic builds the inner model from the matching part of the JSON.

🌟 Case Study: One Enquiry, Several Courses and a Phone Number

A visitor often asks about more than one course, and the form always needs a way to reach them back.

interested_courses: list[str] — more than one course in one field

Each string in the list is checked the same way a single field would be.

You type 
class EnquiryIn(BaseModel):
    name: str
    interested_courses: list[str]


enquiry = EnquiryIn(name="Priya Mehta", interested_courses=["Python Professional", "Office & GenAI"])
print(enquiry.interested_courses)
print(len(enquiry.interested_courses))
Python shows 
['Python Professional', 'Office & GenAI']
2
  1. interested_courses: list[str] accepts zero or more strings, in order.
  2. print(len(enquiry.interested_courses)) shows how many courses came in.

contact: ContactInfo — one model nested inside another

The whole contact object in the JSON becomes a ContactInfo instance, not a plain dictionary.

You type 
class ContactInfo(BaseModel):
    phone: str
    whatsapp: str | None = None

class EnquiryIn(BaseModel):
    name: str
    contact: ContactInfo
    interested_courses: list[str] = []

enquiry = EnquiryIn(

  1. class ContactInfo(BaseModel): is a small model of its own, with two fields.
  2. contact: ContactInfo uses that model as this field's type.
  3. name="Priya Mehta", contact={"phone": "9825012345", "whatsapp": "9825012345"}, passes a plain dict for contact; Pydantic builds the nested model from it.
  4. print(enquiry.contact.whatsapp) reads a field two levels deep, through the nested model.
A nested model field holds another model's data; a list field holds several values of one type.

5 — Why Custom Validator Decorators Wait

Field() checks one field entirely on its own: a length, a range, a required value. Some real rules need more than that. A custom validator is a function that checks a rule across two or more fields together. A start date that must come before an end date is one example.

Pydantic hooks such a function to a model with a decorator, written @field_validator. Writing one needs you to already be comfortable with functions, decorators and the model basics this lesson covers. You will meet it once those feel natural, so each new idea builds on one you already trust. For now, just recognise its shape when you see it in someone else's code.

Syntax — for a later lesson, not this one
@field_validator("field_name")
def check_fn(cls, value):
    ...
One rule, or a rule across fieldsA rule inside one field    → Field()
A rule across two fields   → a validator function, added later
🤔 Try It — Predict the output
def check_dates(start, end):
    return start <= end

print(check_dates("2026-01-01", "2026-01-10"))
