1 — 🤔 Authentication vs Authorization

Two different questions guard every route: who is asking, and what are they allowed to do? Authentication checks who sent the request — a password, a token, a certificate. Authorization checks what that known identity may do.

FastAPI answers each failure with its own status code. 401 means the server does not know who is asking; log in again. 403 means it knows exactly who you are, and still says no.

HTTPException(status_code=401) — no proof of identity at all

This small example runs on its own, with no app behind it yet.

You type 
from fastapi import HTTPException

def get_profile(token):
    if token is None:
        raise HTTPException(status_code=401, detail="Not authenticated")
    return {"token": token}

try:
    get_profile(None)
except HTTPException as exc:
    print(exc.status_code, exc.detail)
Python shows 
401 Not authenticated
  1. if token is None: there is no proof of identity to check.
  2. raise HTTPException(status_code=401, detail="Not authenticated") stops the function with a 401.
  3. except HTTPException as exc: catches it the same way FastAPI would for a real request.

HTTPException(status_code=403) — known, but not allowed

Change one thing from the run above: the caller now has an identity, just not the right one.

You type

try:

2 — 🔄 Never Store Plain-Text Passwords: Hash Them

A hash turns a password into a fixed string that cannot be turned back into the original. Storing the real password instead means one leaked database exposes every account, everywhere that password was reused.

Checking a login never reverses the hash. It hashes the new guess the same way and compares the two hashes. pwdlib picks a strong, modern hash (argon2) so you never choose the algorithm yourself.

Hash a password the moment an account is created. Never log it, print it, or store it anywhere in plain text, not even for a day.

Hashing only runs one way: check a guess against it, but never recover the original text.

🌟 Case Study: Hashing Neha's Counsellor Password

Future Vision keeps two counsellor accounts for this lesson, Neha and Karan, each with its own password.

The same password_hash object both hashes and checks, so the two steps always agree.

3 — 🔍 Understanding a Bearer Token and a JWT

Once a password is checked, the server needs a way to remember you for the next request. A bearer token is a string a client sends in the Authorization header; whoever holds it is treated as that user.

A JWT (JSON Web Token) is one common shape for that string: three base64 parts joined by dots. The header names the algorithm, the payload carries plain claims like a username, and the signature proves neither part changed.

PyJWT builds and checks this signature for you. The signature is made with a secret key, a value only your server knows. It must never sit in code you commit to Git.

The three parts join with dots, header.payload.signature. Change one character and the signature stops matching.

🌟 Case Study: Signing a Token for Neha

The payload only needs one claim for this lesson: sub, short for subject, holding the counsellor's username.

jwt.encode() / jwt.decode() — sign a token, then read it back

Encoding and decoding with the same secret key always agree on the payload inside.

4 — 🔗 Log In and Protect a Route

A login route checks a username and a password, then hands back a token. OAuth2PasswordRequestForm reads those two fields from a submitted form, with no Pydantic model needed.

Checking that form against COUNSELLORS and signing a token is the whole login route. A protected route then needs the opposite check on every later request: is a valid token attached?

OAuth2PasswordBearer pulls the token out of the Authorization header for you. A dependency named get_current_user decodes it and hands back the matching counsellor, or raises 401.

The token signed in step ② is the same one checked in step ④ — no database lookup needed each time.

🌟 Case Study: A Login Route for Future Vision's Counsellors

Only a logged-in counsellor may change Future Vision's enquiry and learner records, from Lesson 6 and 7.

OAuth2PasswordRequestForm — read username and password from a login form

A wrong password still reaches the same check as a correct one; only the result differs.

You type 
from fastapi import HTTPException
from fastapi.security import OAuth2PasswordRequestForm

COUNSELLORS = {

import os

import jwt
from fastapi import Depends, FastAPI, HTTPException
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from pwdlib import PasswordHash

SECRET_KEY = os.getenv("SECRET_KEY", "fvc-dev-only-secret-change-me-in-prod")
ALGORITHM = "HS256"

password_hash = PasswordHash.recommended()

COUNSELLORS = {
    "neha": {"username": "neha", "hashed_password": password_hash.hash("neha-secret-123")},
    "karan": {"username": "karan", "hashed_password": password_hash.hash("karan-secret-456")},
}

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")
app = FastAPI()

ENQUIRIES = [
    {"enquiry_id": "E1", "branch": "Citylight", "course": "Python Professional", "follow_ups": 1},
    {"enquiry_id": "E2", "branch": "Citylight", "course": "Office & GenAI", "follow_ups": 3},
    {"enquiry_id": "E3", "branch": "Pal", "course": "Business Analytics", "follow_ups": 1},
    {"enquiry_id": "E5", "branch": "Vesu", "course": "Excel & Power BI", "follow_ups": 1},
    {"enquiry_id": "E6", "branch": "Pal", "course": "Python Professional", "follow_ups": 1},
    {"enquiry_id": "E7", "branch": "Vesu", "course": "Business Analytics", "follow_ups": 4},
]


@app.post("/token")
def login(form_data: OAuth2PasswordRequestForm = Depends()):
    counsellor = COUNSELLORS.get(form_data.username)
    if counsellor is None or not password_hash.verify(form_data.password, counsellor["hashed_password"]):
        raise HTTPException(status_code=401, detail="Incorrect username or password",
                             headers={"WWW-Authenticate": "Bearer"})
    token = jwt.encode({"sub": counsellor["username"]}, SECRET_KEY, algorithm=ALGORITHM)
    return {"access_token": token, "token_type": "bearer"}


def get_current_user(token: str = Depends(oauth2_scheme)):
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="Invalid or expired token",
                             headers={"WWW-Authenticate": "Bearer"})
    counsellor = COUNSELLORS.get(payload.get("sub"))
    if counsellor is None:
        raise HTTPException(status_code=401, detail="Invalid or expired token",
                             headers={"WWW-Authenticate": "Bearer"})
    return counsellor


@app.get("/enquiries/{enquiry_id}")
def get_enquiry(enquiry_id: str):
    for row in ENQUIRIES:
        if row["enquiry_id"] == enquiry_id:
            return row
    raise HTTPException(status_code=404, detail="Enquiry not found")


@app.delete("/enquiries/{enquiry_id}")
def delete_enquiry(enquiry_id: str, current_user: dict = Depends(get_current_user)):
    for row in ENQUIRIES:
        if row["enquiry_id"] == enquiry_id:
            ENQUIRIES.remove(row)
            return {"deleted": enquiry_id, "by": current_user["username"]}
    raise HTTPException(status_code=404, detail="Enquiry not found")


if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="127.0.0.1", port=8000)

5 — 🔍 Test the Login and Protected-Route Flow

A login system has two paths worth checking: the request that should fail, and the one that should succeed. Testing only the happy path hides a route that never actually rejects anyone.

Because get_current_user depends on OAuth2PasswordBearer(tokenUrl="token"), the /docs page already knows which route issues tokens. An Authorize button appears, so you never paste a token by hand.

What a Production System Still Needs

This login works, but a real deployment needs more. A token's expiry claim, shown above, is only the start.

A real system also offers a scope on each token, limiting what it can do. It also supports an API key for another service calling in, instead of a human logging in.

Go deeper

A refresh token lets a client get a new access token without logging in again. A revocation list lets the server cancel one early, before it expires on its own. OAuth2 scopes limit what one token can do, listed by name. An API key is usually a long random string, checked against a stored list. It needs no username or password at all.
